# 附录：算法服务 Python / FastAPI

> 只写**换项目仍成立**的算法服务约束。标「示例」的条目来自具体项目，进入新仓库前先确认，**不要默认套用**。

## 1. 入口与模块职责

- 先确认服务入口文件、路由模块目录、配置与注册发现目录、消息总线目录的划分，再决定改哪里。
- **优先在现有路由模块中修改，不要额外创建平行入口文件**（平行入口会让同一能力有两套行为，后续无法收敛）。
- 新增接口必须放在既有路由注册链路上，并确认它真的被注册（不是写了文件但没挂上去）。

## 2. 外部依赖的改动边界

- 涉及**配置中心、消息队列、鉴权、服务注册心跳**的改动，范围必须严格限定在需求要求的部分，不做顺手重构。
- 这类改动默认无法在本地完整验证，交付时必须标注"未做真实环境验证"，并说明需要什么环境才能验证。
- 部署相关文件（容器、编排、依赖清单）**未经明确要求不修改**。

## 3. 契约与调用方同步

- 返回结构一旦变化，**必须同步检查后端服务与前端是否受影响**，并按"先确认提供方 → 再改调用方 → 最后调展示层"的顺序调整。
- 契约稳定后要把字段含义与返回结构沉淀成文档/记忆，避免下次再靠读代码反推。
- 算法输出的字段必须能被调用方证明来源；不允许为配合展示而临时拼字段。

## 4. 边界与异常（算法服务的重点）

- **幂等**：同一请求重复到达会怎样？是否会产生重复结果或重复副作用？
- **重复回调 / 重复消费**：消息重复投递时的处理。
- **部分失败**：批量计算中部分失败，返回什么？整体失败还是部分结果？
- **空集合与缺失配置**：空输入、配置项缺失、可选依赖不可用时的错误归属与返回口径。
- **外部依赖不可用**：配置中心/消息队列连不上时，是启动失败还是降级？错误归属在服务自身还是调用方？
- 每条边界都要明确"谁负责表现"，不能把算法侧的数据异常静默变成空结果。

## 5. 依赖与运行

- 依赖从项目指定的依赖清单安装（示例：容器目录下的 `requirements.txt`），不临时 `pip install` 新包；确需新增依赖时先说明必要性与影响范围。
- 使用项目虚拟环境运行，注意各环境路径差异（示例：WSL 与 Windows 路径不同）。
- 搜索与排查时排除产物与虚拟环境目录（示例：`.venv`、`__pycache__`、结果输出目录），避免噪音淹没真实代码。

## 6. 日志与可观测

- 不增加无意义的日志；日志要能定位**输入、关键中间结果、失败原因**。
- 敏感信息不出现在日志里。

## 7. 交付要求

- 说明本次改动的调用链：哪个入口 → 哪些模块 → 输出去哪。
- 明确区分：本地能验证的部分（语法、结构、纯函数逻辑）与必须真实环境才能验证的部分（配置中心、消息队列、注册发现、真实数据）。
