# 个人编码与 AI 协作规范

> 这份规范回答一个问题：**我要求 AI 写代码时，标准是什么、怎么提要求、拿到产出后怎么验。**
> 技术栈无关的部分全在本文件；技术栈特有的部分在 `附录-*.md`，按项目只带走需要的。

---

## 0. 怎么用、怎么迁移、冲突怎么裁决

### 0.1 四层结构

| 层 | 内容 | 放哪 | 换项目是否变 |
| --- | --- | --- | --- |
| 铁律层 | 第 2、3、5、6、7 章：任务分级与 dsh-graph 路由、中文伪代码、先思路后代码、数据来源可证明、编码铁律、交付八项 | 本文件 + 常驻记忆（入口指针只做补充） | 不变 |
| 项目层 | 目录结构、命名、构建命令、框架约定、既有风格 | 目标仓库自己的规则文件 | 每个仓不同 |
| 个人偏好层 | 跨项目恒定、但强度低于铁律的个人习惯：语言与文档风格、脚本选型、表格还是散文 | `个人偏好.md` | 不变，但可被项目覆盖 |
| 技术栈层 | 语言/框架特有的写法与坑（异常归属、注释要求、空态处理等） | 本文件附录 | 换栈才变 |

### 0.2 优先级（冲突裁决）

1. **用户当轮指令**最高：这一轮说改什么就改什么，但不得借当轮指令豁免铁律。
2. **铁律层永远优先**：任何项目规则、任何技术栈习惯都不得豁免第 2、3、5、6、7 章。
3. **项目层 > 个人偏好层 > 技术栈层 > 本规范的默认值**：目录、命名、构建、框架写法一律服从所在仓库；仓库没规定时按个人偏好，个人偏好没覆盖时按附录默认值。
4. **无法判断谁优先时，停下来问人**，不许自行扩大解释、不许静默选一边继续做。

> 个人偏好层**不是**第二个铁律：它只提供默认值，项目规则与它冲突时按项目走，并在交付里说明"按项目规则偏离了个人偏好"。要让某条偏好获得豁免权，那是把它升级进铁律层，去改正文。

### 0.3 迁移到另一台机器

规范本体（正文 + 附录）由 git 仓承载。**推荐一条命令走完安装与校验**：

```powershell
powershell -File ~/.dsh/standards/install/install.ps1    # 首次：目录不存在时会先 clone（pwsh 7 同理）
powershell -File ~/.dsh/standards/install/verify.ps1     # 安装是否真的生效
```

`install.ps1` 做三件事：落地规范本体（clone 或 `-Update` 快进）→ 把入口标记块并入宿主入口文件（块外内容一字不动，重复执行不产生 diff）→ 打印常驻记忆的写入指引。它**不能**替 AI 写记忆，所以第 3 步仍需 AI 会话执行，但 `verify.ps1` 会去记忆存储里查铁律锚点，把"漏了没生效"从静默失败变成红色 FAIL。`verify.ps1` 分五段（standards / entry / memory / project / drift）共 29 项，可用 `-Segment` 只跑相关段、用 `-Json` 输出机器可读结果。

手动等价步骤（脚本不可用时）：

0. **落地规范本体**：`git clone https://gitee.com/ydcy_studio/ai-compilation-specifications.git ~/.dsh/standards`
1. **入口指针**：把 `install/agents-pointer.md` 的内容并入新机器的 `~/.dsh/AGENTS.md`——该文件里那段被 `<!-- BEGIN personal-coding-standards -->` / `<!-- END personal-coding-standards -->` 包裹，**按标记块插入或替换，不要覆盖新机器上原有的其他内容**。
2. **常驻铁律**：把 `install/iron-rules.txt` 交给新机器上的 AI 会话，让它用**记忆工具**写入常驻记忆（说清楚"写进常驻/全局记忆"即可）。

换宿主（Claude Code / Cursor / Codex）不是换一套规则：入口落位见 `install/hosts/README.md`，正文仍是同一份。

**三个必须知道的坑**：

- **不能靠拷 `USER.md`**。常驻记忆的 Markdown 文件是 `memories.json` 的**生成投影**，直接拷贝进去的内容会在下一次记忆写入时被重建覆盖——必须走记忆工具写入，或整体迁移记忆存储。
- **不能只靠 `AGENTS.md`**。宿主对会话规则有字节预算（实测 65536 字节）。当目标项目自己的规则文件很大时，用户级 `AGENTS.md` 会被**静默挤掉、根本不进上下文**——这不是假设，实测已发生过（一个 82KB 规则文件的项目里，用户级 `AGENTS.md` 整个没进上下文）。所以最不可让步的那几条必须同时固化在**每轮都注入**的常驻记忆里，`AGENTS.md` 只当补充入口。
- 正文与指针**不得写死机器相关的绝对路径**，一律用 `~/.dsh/standards/...` 表述。

### 0.4 把规范落到具体项目

新项目接入不是"抄一份规则"，而是按顺序生成项目层规范：

1. 先侦察仓库，留下事实证据（目录、构建、测试、配置、已有规则）；
2. 再建项目规则主文件（目录归属、构建/验证命令、技术栈约定、禁止项、交付要求、已知风险）；
3. 随后按顺序落地提交准则、文档记忆索引、配置样例与规则测试。

**每个项目值都必须能指到目标仓库的文件；无法证明的项列入待确认并问人，AI 不得自主决定。** 完整 0–8 步、必建文件清单与自检表见 README「迁移到具体项目：AI 执行顺序」，填写模板见 `~/.dsh/standards/install/project-spec-checklist.md`，落地后跑 `~/.dsh/standards/install/verify.ps1 -Segment project,drift -Project <目标仓>` 复核。

## 1. 一句话原则

> 你给 AI 的约束越具体，产出质量越高；你要求的缺陷清单越具体，你的判断力成长越快。

不要把 AI 当"写代码的"，把它当**一个会写代码、但需要你定标准和验结果的执行者**。不需要背 API，但必须能说清：输入是什么、输出是什么、边界在哪、并发怎样、错了怎么办、什么条件下这个方案会失效。

## 2. 任务分级、方案确认与 dsh-graph 路由

动手前先给任务定级，级别决定"能不能直接改代码"，以及启用 dsh-graph 时是否必须纳入目标管理。

| 级别 | 判定 | 动作 |
| --- | --- | --- |
| **S** | 文案、局部样式、单点低风险映射、明确且无跨模块影响的小修复 | 可直接执行，不强制创建 graph 目标；交付时说明为什么判定为低风险、改了哪里、怎么静态复核。用户明确要求纳入 graph 时，仍按 graph 流程执行 |
| **M** | 单模块逻辑修改、单接口调用方调整、局部状态或组件行为变化 | **先简短说明方案和影响范围，等确认后再改**；当前会话实际提供 `graph_*` 工具时，确认后必须创建或复用 graph 目标并按生命周期执行 |
| **L** | 跨仓、接口契约、数据库/Mapper、状态流、异步链路、重构、根因不明缺陷、影响多个调用方 | **必须先输出方案并等确认**；当前会话实际提供 `graph_*` 工具时，确认后必须创建或复用 graph 目标并按生命周期执行 |

### 2.1 dsh-graph 强制路由

以下规则仅在当前会话实际提供 `graph_*` 工具、且用户要求执行开发任务时生效；纯讨论、问答、方案比较不创建目标，也不接管主管会话。

1. **M/L 必须走 graph**：创建新目标，或复用用户明确指定的既有目标；禁止一边保留 graph 目标、一边在普通会话旁路完成实现。S 级不强制建目标，但用户明确指定 graph 目标时不再适用直接执行例外。
2. **当前任务会话先接管**：用户确认执行 M/L 方案，或明确要求执行某个 graph 目标，即视为授权当前发出任务的会话调用 `graph_claim_supervisor`；接管必须发生在该目标的主管操作和执行之前，避免后续交互落到旧主管会话，无需为同一次接管重复询问。
3. **既有目标优先**：用户指定目标时不得重复建目标；先读取目标描述、质量判据、状态、上下文卡片、历史 attempt 与 handoff，再从当前阶段继续。
4. **复杂度升级立即切换**：执行中从 S 升为 M/L，或从 M 升为 L 时，立即停手并按新级别补充方案与确认；需要 graph 的，先把已有证据和改动状态写入目标上下文，再继续执行，不能以"已经改了一半"为由绕过。
5. **主管与执行职责分离**：常规 M/L 功能开发中，主管会话只做规划、判据、派发、把关和复核，具体实现通过 graph attempt 执行；不得用普通子代理或主管亲自实现来绕过目标、attempt 和状态记录。
6. **规则治理例外**：规则、规范、协作机制等文字治理任务仍用 graph 管理 M/L 目标、判据、状态和 review，但不强制派执行子代理，可由已接管的主管主会话直接实施；子会话因沙箱或权限无法写目标位置时，应停止子会话并由主管接手。此例外不适用于常规功能开发，不得借此扩大到业务代码实现。
7. **失败不降级**：graph 不可用、接管失败、状态门禁不满足或 attempt 无法建立时，明确报告具体阻塞；除上一条规则治理例外外，不得静默退回普通会话直接实现。
8. **人工关口保留**：使用 graph 不等于自动授权。方案确认、质量判据确认、开始执行、review verdict、发布/交付等关口仍按 graph 规则由负责人裁决；主管不得自行把 `review` 迁为 `delivered`。
9. **交付可追踪**：M/L 交付必须列出 goal ID、attempt ID（未派发或取消时说明原因）、逐条判据状态、静态证据与未验证项；状态不是完成证据，产出物和验证结果才是。

- 执行中复杂度升高（S→M/L、M→L），必须按新级别暂停补充说明，重新确认后再继续。
- M/L 方案必须包含：**目标行为、数据来源、修改入口、影响范围、边界状态、本次不处理的范围**——缺任何一项不得进入实现。
- 分析中发现原方案的数据来源、归属层或影响范围不成立，必须暂停并重新说明调整后的方案。

## 3. 中文伪代码（编码实现第一条，强制）

### 3.1 规则

实现类任务必须写**中文伪代码**，形式是**直接写在实现代码内部的编号注释**：

- 在主流程方法体里，用 `// 1. 业务动作`、`// 2. 业务动作` 标出关键步骤，说明这一步在做什么、数据从哪来、边界怎么处理；
- **不必逐行注释**：只在关键步骤前写，简单赋值、getter/setter、重复的循环体不需要编号；
- **不是实现前单独输出一份伪代码文档或对话段落**，也不是等我确认的前置关卡；编号注释随代码一并交付，我用它事后核对实现思路；
- 不许跳过、不许用英文替代、不许写"先查询再处理再返回"这种没有信息量的概括。

> 与 M/L 方案的区别：M/L 级的"先思路后代码"方案仍是实现前的文字说明（目标行为、数据来源、影响范围等）；伪代码不是方案文档，它落在代码里。方案里可以预告关键步骤，但以代码中的编号注释为准。

### 3.2 标准写法（照着写）

```text
public 结果 方法(入参) {
    // 1. 过滤订单：状态 != CANCELLED 且 payTime != null
    ...

    // 2. 按 userId 分组
    ...

    // 3. 每组把 totalAmount 累加，得到 Map<userId, 总金额>
    ...

    // 4. 按金额从高到低排序
    // 5. 用 LinkedHashMap 装排序后的结果并返回
    ...
}
```

特征：**编号步骤 + 业务语义 + 具体到字段和数据结构 + 写在实现代码里 + 不写语法级细节**。

### 3.3 编号注释必须交代到的内容

- **数据从哪来**：哪张表/哪个接口/哪个入参，过滤条件是什么。
- **中间结构长什么样**：Map / List / 对象，key 是什么，value 是什么。
- **排序与顺序要求**：按什么字段、升序降序、是否要求稳定顺序（如 LinkedHashMap）。
- **空值与异常分支怎么走**：空集合返回空还是报错、单条怎么处理。
- **返回结构**：字段清单，谁用这个结果。

### 3.4 编号注释与实现的关系

- 编号注释就是实现的一部分，写在对应步骤的代码之前，**不另外产出"伪代码段落"**；交付说明可以引用步骤编号，但不要重复贴一份。
- 编号与实现位置必须能逐一对应；对不上就是实现偏离思路的直接证据，也是我核对时的第一入口。
- 实现中发现步骤要改（数据来源不对、字段不存在、顺序要求做不到），**直接改代码里的编号注释并说明为什么改**，不许代码改了、注释还停在旧思路。

### 3.5 反例

| 反例 | 问题 |
| --- | --- |
| 实现前单独输出一份"伪代码"文档，代码里没有对应编号注释 | 两处必然漂移，核对时不知道以哪份为准 |
| 每一行都写注释/编号 | 噪音，掩盖真正的关键步骤 |
| `// 1. query orders 2. group by user 3. sum` | 英文、无字段、无数据结构，等于没写 |
| 代码里没有任何编号步骤注释，直接贴 200 行实现 | 没有可核对的思路，只能逐行读代码 |
| `// 1. 处理数据 2. 返回结果` | 没有业务信息，无法验证是否理解正确 |

## 4. 动手前必须定清的四件事

对不上任何一件，**停止实现并问人**，不许用猜测兜底。

### 4.1 数据来源必须可证明

参数/字段的来源分三类，回答时必须区分，禁止混用：

| 类型 | 含义 | 举例 |
| --- | --- | --- |
| 静态可确定 | 字面量、常量、枚举、配置固定值、明确默认值 | `MAX_RETRY = 3` |
| 链路可确定 | 能从上游调用、DTO 字段、请求参数、SQL 映射、配置绑定明确追溯 | Controller 传入的 DTO 字段 |
| 仅运行时可确定 | 前端输入、请求体、数据库实时数据、消息队列、缓存、定时任务上下文、第三方返回 | 用户提交的表单值 |

- 对"仅运行时可确定"的参数，**禁止臆测具体值**、禁止为了给答案而编造示例值。
- 只要调用链还能往下追，就继续追到入口层（Controller/API、消息消费者、定时任务入口、事件监听、前端调用入口、测试或 mock 构造处），不许停在"大概是"。
- 必须区分：**实际传入值 / 方法内归一化后的值 / 允许的输入格式 / 兜底处理后的值**，四者不得混为一谈。
- 代码里存在 normalize / fallback / default，必须说明触发条件、是否覆盖当前链路；**不能因为有 fallback 就把 fallback 当成真实入参**。

### 4.2 输出契约

返回类型、字段清单、顺序要求、空值口径（空集合 / null / 默认值 / 报错）必须是明确的。改结构必须同步调用方和注释。

### 4.3 边界状态

初始态、加载态、成功态、空态、失败态、重复触发、取消/关闭/切换后的状态清理，逐项确认。

### 4.4 停止实现的触发条件（出现即停）

- 数据来源无法证明、字段真实存在性无法确认。
- 接口提供方与调用方契约冲突。
- 现有代码行为与描述不一致。
- 判断依赖真实运行数据、日志、请求样例、数据库记录或外部服务状态，而当前没有证据。
- 修改范围会扩大到多个模块或仓库，而需求只描述局部现象。
- 只能靠临时兜底、相似字段、猜测默认值或隐藏错误来完成表象修复。

停下来要写清：已追踪到哪一层、缺哪一段证据、需要什么补充信息（请求样例 / 日志 / 断点结果 / 测试数据 / 数据库记录）。

## 5. 编码铁律（数值可核对）

### 5.1 结构

- 单方法 **< 80 行**，超了按职责拆分。
- 控制结构嵌套 **≤ 3 层**，超了用提前返回、提取方法、拆流程降低。
- 方法入参 **< 5 个**，超过 4 个封装成有业务含义的参数对象 / DTO / 配置对象。
- 同一段逻辑**复用超过 3 次必须封装**；但重复出现两次不必然抽象，只有"表达同一业务规则且后续会共同演进"才抽。

### 5.2 命名

- 命名承载业务含义；不得用 `data`、`item`、`temp`、`result2` 承载关键概念。
- 新增业务概念、状态名、DTO 字段、缓存 key、事件类型、枚举值、方法名前，**先搜索已有命名和相邻模块用法**；已有稳定命名必须沿用。
- 确需新增命名时，必须说明它与旧概念的区别，不能用同义词制造并行概念。
- 不得用相似字段名掩盖数据来源差异；命名要体现查询条件、资源身份、展示结果、运行状态等不同概念边界。

### 5.3 单一主入口

- **优先修改原主路径并收口旧逻辑，不默认叠加平行实现**；用户说"改现有方法"时，优先改原方法而不是新增一个替代它。
- 新逻辑替代旧逻辑时，能删就删；暂不能删必须说明保留原因和仍在使用它的调用方。
- 修复后检查同一业务规则是否在多处重复实现，重复则收敛到共享入口。

### 5.4 diff 只呈现本次行为变化

- 不夹带无关格式化、批量重排、无关 import 调整、大范围重命名、顺手清理。
- 必须做结构调整/重命名/抽取/删旧逻辑时，说明原因、影响范围、以及为什么不能用更小改动完成。
- 抽象后必须让调用方更清楚，不能隐藏关键业务差异；需要大量参数开关的抽象不如保留清晰的局部实现。

### 5.5 注释

- 注释只解释**业务原因、边界条件、非显然约束、数据来源**，不解释代码字面动作。
- 关键实现处必须说明：数据来源、业务规则、异常触发条件、分支意图、非显而易见转换、以及**不做兜底的原因**。
- 禁止无信息量注释和过期注释。

### 5.6 不兜底

- **不做无来源字段、相似字段或隐藏错误的业务兜底**；兜底不能掩盖错误的验证结果。
- 不静默吞异常；异常必须在**归属层**抛出具可定位的信息。

### 5.7 依赖与配置

- 新增依赖、改构建配置、改环境变量、改外部依赖配置前，说明必要性和影响范围。
- 不为单个小功能引入重型依赖，优先用项目已有框架和本地约定。
- 不提交密钥、token、真实账号、真实连接串或其他敏感配置。

### 5.8 保护用户已有改动

- 改前在目标仓库看状态，识别用户已有改动，**避开或兼容**。
- 不用 reset / checkout / clean 等方式覆盖用户改动。
- 修改的文件已有非本任务改动时，先读相关 diff，只做兼容本任务的局部修改。

## 6. 交付必附八项（每次实现类交付都要有）

1. **实现思路**：关键步骤与设计理由；步骤与代码里的中文伪代码编号注释一致，不另外重复贴一份。
2. **实现代码**：完整可运行，关键步骤用中文编号注释（伪代码），与实现位置对应。
3. **优势**：好在哪，适合什么场景。
4. **缺陷**：可能出问题的 3 个场景，**按严重程度排序**（不许列 10 条无关紧要的）。
5. **边界**：数据量扩大 100 倍、并发、空值、异常输入时分别会怎样。
6. **替代方案**：一个更简单但稍慢的版本，**说明牺牲了什么**。
7. **验证方法**：3 个测试用例，含正常、边界、异常。
8. **常见误用**：这段代码最容易被误用的地方是什么。

> 八项的价值在于强迫从"写代码"切换到"交付方案 + 自审"。拿到的不只是答案，还有判断素材。

## 7. 交付格式（收尾必须回答）

| 字段 | 要求 |
| --- | --- |
| 任务级别 | S / M / L，以及低风险判定理由（S 级） |
| 数据来源 | 明确到表/接口/字段；不确定就写"未验证、缺证据" |
| 修改点 | 文件 + 方法 + 行为变化，分仓库列 |
| 自审结果 | 是否满足 80 行/3 层/5 参/复用 3 次、有无死代码与重复逻辑、diff 是否干净 |
| 验证情况 | 执行了哪些验证；**没执行测试/构建/lint/联调就明确说没执行** |
| 未验证风险 | 依赖真实环境（数据库、缓存、消息队列、浏览器、多实例）才能确认的部分 |
| 提交记录 | 每个提交的 hash + 一句话范围；是否超出提交粒度阈值（400 行 / 12 个非生成文件），超了说明拆分计划或不可拆原因 |
| 涉及仓库 | 改了哪几个仓；跨仓任务分仓说明状态与 diff |

补充要求：

- 结论必须标明**已验证 / 静态推断 / 未验证**，不得把静态检查说成联调通过。
- 未执行测试时，至少做最小静态复核：import、类型、字段名、调用方/提供方契约、有无空占位、死代码、未使用变量。
- 规则类改动要额外说明同步了哪些规则文件与记忆。
- 提交粒度按《附录-提交准则》执行：一个提交 = 一个可独立审查/验证/回滚的逻辑单元，超硬上限必须拆分或在交付中说明原因；每个提交附验证结果。

## 8. 验收清单（拿到产出后逐条过）

不需要每次全验，但**每次至少挑 1 条亲手跑一遍**——这是把 AI 的知识转成自己判断力的过程。

**输入输出**
- [ ] 入参为 null / undefined / 空集合会怎样？
- [ ] 输入超长、超大、特殊字符会怎样？
- [ ] 返回 null 还是空集合？调用方处理了吗？

**边界与异常**
- [ ] 空数据、单条数据、海量数据分别会怎样？
- [ ] 重复数据、并发请求、超时会怎样？
- [ ] 异常被吞了吗？错误信息够定位吗？

**性能与资源**
- [ ] 数据量扩大 100 倍，哪里先崩？
- [ ] 有没有不必要的循环、查询、渲染？
- [ ] 内存、连接、文件句柄会泄漏吗？

**安全与兼容**
- [ ] 有注入、越权、脱敏、重放风险吗？
- [ ] 浏览器/版本/设备/系统兼容吗？
- [ ] 敏感信息有没有打进日志？

**可维护**
- [ ] 有没有修改入参？
- [ ] 命名、分层、注释清楚吗？
- [ ] 有没有更简单的写法？
- [ ] 这段代码最容易被误用的地方是什么？

## 9. 提示词模板

### 9.1 通用模板（任何技术栈、任何任务）

```
【任务】
用 [技术栈/语言] 实现 [具体功能]。

【背景】
- 业务场景：[一句话说明这个功能解决什么问题]
- 使用者：[谁用，什么频率，什么环境]
- 现有系统：[新建还是在已有系统上改，依赖什么]

【输入】
- 数据来源：[接口/用户输入/文件/数据库/消息队列]
- 数据结构：[字段、类型、含义]
- 数据规模：[量级、频率、峰值]

【输出】
- 返回类型/格式：[JSON/HTML/对象/文件]
- 顺序要求：[有序/无序/按某字段排序]
- 空值处理：[返回空/null/默认值/报错]

【约束】
- 性能：[响应时间、吞吐量、内存限制]
- 兼容：[浏览器/版本/设备/系统]
- 安全：[鉴权、脱敏、防注入、防重放]
- 可维护：[分层、命名、注释、测试]
- 禁止项：[不用某库、不用某语法、不改某文件]

【必须同时给出】
1. 实现思路：关键步骤与设计理由，与代码中的中文伪代码编号注释一致；
2. 实现代码：完整可运行，关键步骤用中文编号注释（伪代码）；
3. 优势：这个方案好在哪，适合什么场景；
4. 缺陷：可能出问题的 3 个场景，按严重程度排序；
5. 边界：数据量扩大 100 倍、并发、空值、异常输入时会怎样；
6. 替代方案：一个更简单但稍慢的版本，说明牺牲了什么；
7. 验证方法：3 个测试用例，含正常、边界、异常；
8. 常见误用：这段代码最容易被误用的地方是什么。
```

### 9.2 场景 1：写新功能

```
实现 [功能]。
要求：
- 中文伪代码直接写进实现代码：在主流程方法体用 // 1. xxx、// 2. xxx 标出关键步骤，不必逐行注释，不要单独再给一份伪代码文档；随代码一并交付，不要为等我确认而停下；
- 编号注释要说明数据来源、业务规则和边界，并与实现位置对应；
- 最后列出 3 个测试用例，包含正常、边界、异常。
```
*为什么这样问：编号注释就写在实现步骤上方，核对时不必逐行读 500 行代码；注释与实现位置对齐后，思路偏离一眼可见。*

### 9.3 场景 2：重构旧代码

```
下面是我的代码：
[粘贴代码]

请：
1. 指出 3 个最严重的问题，按严重程度排序；
2. 每个问题说明：什么场景下会出 bug，不要泛泛说"可读性差"；
3. 给出重构后的代码；
4. 说明重构后引入了什么新风险；
5. 如果我只想改一处，应该先改哪里。
```
*为什么这样问：重构最怕大改一通看不出哪里变了。要求"按严重程度排序"和"新风险"，才能判断值不值得改。*

### 9.4 场景 3：审查 AI 生成的代码

```
这是 AI 生成的代码：
[粘贴代码]

请以代码审查者身份回答：
1. 这段代码在什么输入下会出错？
2. 有没有空指针、并发、事务、性能、安全问题？
3. 有没有更简单但等价的写法？
4. 如果这段代码上线，你最担心什么？
5. 给出 3 个能暴露问题的测试用例。
```
*为什么这样问：AI 审查 AI 的代码能发现注意不到的坑；再拿测试用例亲手跑一遍，坑就变成经验。*

### 9.5 场景 4：学习某个 API / 函数 / 库

```
我不需要背这个 API，我需要知道它的用途和缺陷。
请讲 [函数/API/库名]：
1. 最典型的 3 个使用场景，每个给一段最短代码；
2. 最容易踩的 3 个坑，每个说明触发条件和现象；
3. 和它最容易混淆的 API 是什么，区别在哪；
4. 什么情况下绝对不要用它；
5. 给一个能复现坑的最小示例，我要自己跑；
6. 它在不同技术栈/版本下行为有差异吗？
```
*为什么这样问：最后两条是关键。坑跑一遍才算内化；技术栈差异能防止套用错场景。*

### 9.6 场景 5：调试

```
我遇到这个异常/现象：
[粘贴异常栈或现象描述]

相关代码：
[粘贴代码]

请：
1. 列出最可能的 3 个原因，按概率排序；
2. 每个原因给出验证方法，不要直接给修复方案；
3. 告诉我怎么用断点/日志/抓包/监控确认是哪一个；
4. 确认后再给修复方案。
```
*为什么这样问：直接要修复方案会跳过定位过程；"先验证再修复"才能建立排查直觉。*

### 9.7 场景 6：技术选型

```
我要在 [场景] 下选择 [A] 还是 [B]。
背景：
- 数据规模：[量级]
- 并发：[QPS/用户数]
- 团队：[技术栈/人数]
- 约束：[时间/成本/运维能力]

请：
1. 列出两者的核心差异，按对当前场景的影响排序；
2. 各自适合什么场景，不适合什么场景；
3. 给出推荐，并说明推荐理由；
4. 推荐方案在什么条件下会变成错误选择；
5. 如果选错了，迁移成本有多大。
```
*为什么这样问：最怕列一堆对比表格却不告诉"什么条件下会错"。"错误条件"+"迁移成本"才能做判断。*

### 9.8 场景 7：性能优化

```
这段代码/这个接口/这个页面在 [场景] 下性能不达标。
现象：[具体指标，如首屏 3 秒、接口 2 秒、CPU 80%]
数据规模：[量级]

请：
1. 按优先级列出最可能的瓶颈，每项说明判断依据；
2. 每项给出验证方法，不要直接优化；
3. 确认瓶颈后再给优化方案；
4. 每个优化方案说明：提升多少、引入什么新风险、什么场景下反而更慢；
5. 如果只能改一处，先改哪里。
```
*为什么这样问：性能优化最怕盲目优化。"先验证再优化"+"反而更慢的场景"才能避免负优化。*

### 9.9 场景 8：架构设计

```
我要设计 [系统/模块]。
背景：
- 业务：[做什么]
- 规模：[用户量/数据量/并发]
- 团队：[人数/技术栈]
- 约束：[时间/成本/现有系统]

请：
1. 先给 2—3 种架构方案，各自的核心理念；
2. 每种方案给出：模块划分、数据流、关键选型；
3. 每种方案说明：适合什么场景、不适合什么场景、什么条件下会崩；
4. 给出推荐，并说明推荐理由；
5. 推荐方案在什么条件下需要重构，重构成本多大；
6. 最后给一个最小可行版本，说明先做什么、后做什么。
```
*为什么这样问：最怕一上来就是微服务 + 中台 + 云原生。"2—3 种方案"+"什么时候会崩"才能做取舍。*

## 10. 反模式：不要这样问

| 错误问法 | 问题 | 正确问法 |
| --- | --- | --- |
| "帮我写个登录功能" | 约束太少，只会给最普通的写法 | "实现登录，JWT + 刷新 token，失败 5 次锁定 10 分钟，密码 bcrypt，返回统一错误码" |
| "这段代码有什么问题" | 太泛，给一堆无关紧要的 | "这段代码在并发和空值下有什么问题，按严重程度排序" |
| "有没有更好的写法" | "更好"没标准 | "有没有更简单、但性能稍差的写法？牺牲什么换什么？" |
| "帮我优化一下" | 可能过度设计 | "只改这一处，其他不动，说明改动理由和新风险" |
| "这个 API 怎么用" | 只得到用法，得不到判断 | "这个 API 的用途、缺陷、禁用场景，各给一个例子" |
| "帮我设计个架构" | 会给最流行的，不一定适合 | "给我 2—3 种方案，各自适合什么场景、什么条件下会崩" |
| "用哪个框架好" | 没有背景，无法判断 | "数据 10 万、团队 3 人、两周上线，A 和 B 选哪个，什么条件下会选错" |

## 12. 实现后自审清单

- [ ] 有没有重复逻辑、无来源字段、相似字段兜底、过时分支、状态未清理、命名不清？
- [ ] 新增/修改的方法是否 < 80 行、嵌套 ≤ 3 层、入参 < 5 个、复用 > 3 次的逻辑是否已封装？
- [ ] 是否新增了长函数、混合层级函数或难以阅读的复杂条件？
- [ ] 新逻辑是否替代旧逻辑？该删的删了吗？没删的说明原因和调用方了吗？
- [ ] diff 是否符合"只呈现本次行为变化"？
- [ ] 半年后回看是否容易读懂？业务规则是否散落？调用链是否比改前更绕？

## 13. 常见误用（针对这份规范本身）

| 误用 | 后果 | 纠正 |
| --- | --- | --- |
| 把伪代码当形式，写一行"先查询再返回"就完事 | 无法核对实现，伪代码等于没给 | 伪代码必须交代数据来源、中间结构、排序、空值分支 |
| 把伪代码当成实现前单独输出的文档，代码里没有编号注释 | 两处必然漂移，核对时不知道以哪份为准 | 伪代码写在代码内部的编号注释里，交付说明只引用步骤 |
| 铁律层被"项目习惯"顶掉（例如"这个仓一直这么写"） | 底线漂移，坑会重复踩 | 铁律层不可豁免；项目只能决定技术写法 |
| 把个人偏好塞进铁律（或把铁律写成"偏好"） | 底线被稀释，或习惯被当成硬约束 | 违反出事故的进铁律；跨项目可让步的进 `个人偏好.md` |
| 只把规范放 `AGENTS.md` | 项目规则大时被预算挤掉，等于没生效 | 铁律固化进每轮注入的全局记忆 |
| 八项交付只要前两项 | 拿不到判断素材，只剩代码 | 缺陷/边界/替代方案/测试用例是硬要求 |
| 验收清单每次都不跑 | 永远停在"看起来对" | 每次至少挑一条亲手验证 |
