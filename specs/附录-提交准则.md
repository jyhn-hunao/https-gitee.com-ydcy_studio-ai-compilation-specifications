# 附录：提交准则（Git Commit）

> 解决的问题：AI 常把 Git 提交当成"保存点"——每改一个文件、每跑一次工具就提交一次；或者相反，把几个不相关的需求攒成一次巨型提交。
> 前者看不出一次完整作业的量，后者没人愿意直接审查。本附录只规定"一个提交应该多大、怎么切、怎么写、怎么验"，不涉及具体分支模型。

---

## 0. 一句话原则

> **一个提交 = 一次人类可复述的作业**：能用一句话说清"做了什么、为什么"，能独立构建、独立验证、独立回滚，审查者 20 分钟内能看完并给出通过/不通过。

合格提交的三个硬条件，缺一不可：

| 条件 | 判据 | 不合格的表现 |
| --- | --- | --- |
| 单一意图 | 标题一句话说清；diff 只服务这一件事 | "顺手"改了别的模块、格式或命名 |
| 独立可验证 | checkout 该提交后，相关编译/测试/页面可用，不依赖后续提交 | 提交后编译不过，要等下一个提交才恢复 |
| 可审查 | `git show --stat` 在阈值内，评审能一次读完 | 几百个文件上万行；或只有 1 行且没有上下文 |

补不齐时先拆或先补验证，不要"先提交再说"。

---

## 1. 提交单元怎么划

一个提交单元 = **一个需求点 / 一个缺陷 / 一次重构 / 一次迁移 / 一次规则调整**，不是"一次编辑动作"。

| 场景 | 一个提交放什么 | 不要放什么 |
| --- | --- | --- |
| 新功能 | 该功能的完整链路 + 其测试 + 必要文档 | 另一个功能、顺手重构、格式化 |
| 缺陷修复 | 复现用例（如有）+ 修复 + 相关测试 | 无关清理、"反正看到了"的改动 |
| 重构 | 行为不变的结构调整 + 证明行为不变的测试 | 行为变化（另开 feat/fix） |
| 契约变更 | 契约（DTO/接口/XML）+ 消费方 + 前端字段 | 同批的样式优化、文案 |
| 数据库迁移 | 版本化脚本（标注未执行）+ 对应实体/Mapper | 多个不相关批次的大 SQL |
| 纯文档/规则 | 一个主题的文档或规则调整 | 混入代码改动 |

判断口诀：**"如果审查者只回滚这一个提交，系统是否仍然自洽？"** 否，就说明单元没切好。

补充：

- 同一逻辑单元内的多次修补（改错字、调参数、补边界）在**未推送前**用 `git commit --amend` 或 `git rebase -i` 收敛，不制造"fix 上一个提交"的链条。
- 测试与实现同属一个单元时**不要拆开提交**，否则中间提交测试红、无法独立验证。
- 不在一个提交里夹带格式化/重命名/import 排序；这类机械改动单独提交（`style`/`chore`），并注明"无行为变化"。

## 2. 粒度上下限（数值可核对）

以**非生成文件**统计（排除 lock 文件、构建产物、快照、批量导入数据、自动生成的协议/夹具；纯文档按同一阈值）：

| 维度 | 理想带 | 硬上限 | 超过硬上限怎么办 |
| --- | --- | --- | --- |
| 文件数 | ≤ 8 | 12 | 拆分；确实不可拆时在正文写"为何不可拆"，由审查者确认 |
| 变更行（新增+删除） | 50–300 | 400 | 同上；纯机械大改可单独提交并标注 |
| 审查时长 | ≤ 20 分钟 | 30 分钟 | 超过就拆，不要求审查者硬读 |

下限（防止"碎提交"）：

- 变更 **< 20 行**且不属于"文案/配置/单行修复/依赖版本/锁文件"时，说明它为什么必须独立成一次提交，否则并入相邻的逻辑提交。
- 禁止把**一个逻辑单元**按文件拆成多次提交（"每文件一提交"），也禁止按工具动作/保存时间自动提交。
- 提交数量不是工作量；碎片化提交只会让回溯和 blame 变难。

> 数值不是教条：项目可以把上限收紧；要放宽必须在项目规则里写明理由（例如首次引入生成代码、单文件迁移脚本），并经负责人确认。

---

## 3. 拆分与合并策略

**拆分顺序**（从大到小）：

1. 按意图：`feat` / `fix` / `refactor` / `perf` 不混；
2. 按层：契约 → 后端实现 → 前端消费 → 测试/文档（每层结束都可构建）；
3. 按阶段：骨架（可运行的空壳）→ 主链路 → 边界与异常 → 样式/交互 → 测试与文档；
4. 机械改动单独：格式化、重命名、依赖升级、批量替换。

**大改动必须"边写边拆"**，不是写完之后再按文件切开。拆出来的每个提交都要能单独通过项目的编译/测试；做不到时，说明原因（例如跨层强耦合的重构），并给出替代方案（合并为一个提交 + 正文解释 + 更细的审查说明）。

**合并规则**：同一意图的碎片化微调合并为一个提交；但不得为了"显得小"把不相关改动硬凑在一起，也不得为了"显得完整"把多个需求打包。

## 4. 提交前 gate（硬性）

按顺序执行，任何一项不通过就不提交：

- [ ] `git status` / `git diff` 看过，暂存区只包含本次意图的文件；
- [ ] 逐块 `git add -p`，不用 `git add -A` 一把梭；
- [ ] 按项目命令跑过编译/测试/静态检查；**未执行就写明原因**，不把"没报错"说成"验证通过"；
- [ ] 无调试残留：临时日志、`console.log`、注释掉的代码、临时开关、mock 数据；
- [ ] 无密钥/账号/token/真实连接串；无 `.env`、日志、构建产物、依赖目录；
- [ ] 该提交单独 checkout 后，相关模块仍可构建/运行（或已说明依赖关系）；
- [ ] SQL 变更已落盘并标注"未执行、待人工执行"；
- [ ] 提交信息符合第 5 节；
- [ ] `git diff --cached --stat` 未超第 2 节硬上限。

---

## 5. 提交信息

格式：

```
<type>(<scope>): <摘要>

<正文：为什么 / 改了什么 / 影响面 / 验证 / 风险与回滚>
```

- **type**（小写）：`feat` 新功能、`fix` 缺陷修复、`refactor` 行为不变的重构、`perf` 性能、`test` 测试、`docs` 文档、`style` 纯格式、`build` 构建/依赖、`chore` 杂项、`revert` 回滚。
- **scope**：受影响的模块/端（如 `backend`、`frontend`、`sdk`、`pipeline`、`dbsql`），由项目定义词表。
- **摘要**：≤ 50 个字符；动宾结构，说清"做了什么"；**中文可以，但不要只有"优化/修改/更新"**；结尾不加句号。
- **正文必写**：变更 > 50 行、跨层/契约变更、数据库迁移、性能改动、含风险或回滚步骤。正文用固定小标题，便于审查：

```
为什么：
改了什么：
影响面：
验证：
风险/回滚：
```

- **footer**：关联单号 `Refs: #123`；破坏性变更 `BREAKING CHANGE: ...`；多仓任务在正文列出各仓提交。

反例 → 正例：

| 反例 | 问题 | 正例 |
| --- | --- | --- |
| `1` / `b` / `update` | 无法检索与回溯 | `fix(frontend): 修正大屏年份标签遮挡` |
| `UI优化。` | 无范围、无动作 | `style(frontend): 收紧标签右键菜单间距` |
| `bug fix` | 哪个 bug、影响谁 | `fix(backend): 缺测变量导致打标任务失败` |
| `修改` | 等于没写 | `refactor(pipeline): 打标结果改为流式写入` |

## 6. 禁止项

| 禁止 | 原因 |
| --- | --- |
| 每个工具动作/每次保存自动提交 | 碎提交不可回溯，看不出作业量 |
| 一个提交混多个需求 | 无法单独审查/回滚 |
| WIP、fixup、临时备份提交进主线 | 污染历史；未推送前应收敛 |
| 提交生成物、日志、`.env`、密钥 | 泄密与仓库膨胀 |
| 提交信息写 `1`、`update`、`fix bug`、`优化。` | 历史不可检索 |
| 对已推送提交 amend / force push | 破坏他人历史；除非团队明确授权且用户确认 |
| 用 merge 提交掩盖未整理的本地提交 | 审查粒度失控；本地先整理再合并 |
| 为凑阈值虚拆（拆出不能运行的提交） | 违反"独立可验证" |

## 7. 审查者视角（拿到提交后先看什么）

1. `git log --oneline`：标题能否看出范围与意图；
2. `git show --stat`：是否超阈值、是否混入无关文件；
3. 正文：为什么、影响面、验证证据是否齐全；
4. 抽查 diff：是否只有本次行为变化，有无兜底/调试残留。

四问全过才进入逐行审查；任一不过，**退回拆分或补验证**，不要"边审边猜"。

- 未推送：要求 `rebase -i` 整理后重提；
- 已推送：不重写历史，后续按本准则拆分，并在交付说明中记录"该提交超限的原因与后续拆分计划"。

---

## 8. AI 协作约定（针对"每次修改就提交"）

1. **先计划后提交**：任务开始时给出提交拆分计划（N 个提交、各自范围、顺序）；执行中范围变化就更新计划。
2. **只在逻辑单元完成且验证通过后提交**；禁止每改一个文件、每跑一次工具就 `git commit`。
3. **未推送前的修补用 amend/squash**；不要新增 `fix: 修正上一个提交` 这类噪音提交。
4. **预计超阈值先拆**：大功能按"骨架→主链路→边界→样式→测试/文档"分批写、分批提交。
5. **不虚报**：每个提交的验证结果如实写；未跑就写未跑，不把静态检查说成联调通过。
6. **不 push**：除非项目规则明确授权且用户确认；默认只落本地，由人推送。
7. **交付附提交清单**：

| hash | 范围 | 文件/行数 | 验证 |
| --- | --- | --- | --- |
| `abc1234` | 大屏栅格与缩放 | 2 / 180 | `npm run build` 通过 |

8. 拆分不得破坏可构建性；做不到时停下来说明，不用"反正后面会修"掩盖。

## 9. 自检命令与可选钩子

```powershell
# 1. 暂存区概览
git status --short
git diff --cached --stat

# 2. 粒度检查（排除锁文件/构建产物；阈值按第 2 节）
$exclude = '(^|/)(package-lock\.json|pnpm-lock\.yaml|yarn\.lock|node_modules|dist|target|build|\.venv|__pycache__)(/|$)|\.(min\.js|map|snap)$'
$files = 0; $lines = 0
git diff --cached --numstat | ForEach-Object {
    $add, $del, $path = $_ -split "`t", 3
    if ($path -match $exclude) { return }
    $files++
    if ($add -ne '-') { $lines += [int]$add }
    if ($del -ne '-') { $lines += [int]$del }
}
"暂存：$files 个文件 / $lines 行"
if ($files -gt 12 -or $lines -gt 400) {
    Write-Warning "超过提交硬上限（12 文件 / 400 行）：请拆分，或说明为何不可拆"
    exit 1
}
```

```bash
# 3. 复核最近提交的粒度
git log --oneline -10 --shortstat
```

可选：把粒度检查放进 `.git/hooks/pre-commit`（仅本机、不入库），或接进 CI 做提示；**钩子只提示/拦截超限，不得自动提交**。

## 10. 项目接入清单

1. 项目规则文件加一行入口指向本附录；
2. 写明数值覆盖（更严可以；放宽必须给理由）与排除规则（生成物、迁移脚本、数据导入）；
3. 写明验证命令（编译/测试/前端构建/规则测试）与"未执行"的写法；
4. 写明远程策略（是否允许 push、由谁执行、分支保护）；
5. 启动后第一周统计最近 20 个提交，确认落在理想带或已有拆分记录。

## 11. 与其他规范的关系

- 与《个人编码与AI协作规范》§5.4"diff 只呈现本次行为变化"：那条是提交可审的前提，本附录把它量化到提交单元与阈值。
- 与交付八项：交付时增加"提交清单"（第 8 节表格），不替代八项。
- 与项目规则冲突：**用户当轮指令 > 项目规则 > 本附录默认值**；但"单一意图、独立可验证、信息可读"三条不豁免。

---

## 12. 反模式（针对本附录自身）

| 反模式 | 后果 |
| --- | --- |
| 只看行数拆分，不看意图 | 拆出互相依赖、单独跑不起来的提交 |
| 为了"小"把测试或契约拆到后续提交 | 中间提交不可验证，bisect 失效 |
| 用 amend 改写已推送提交 | 他人历史断裂 |
| 提交信息写得像变更日志（逐文件罗列） | 看不出意图；应写 why + 影响面 |
| 超限提交只写"改动较大" | 审查者无法判断风险，等于没解释 |
| 把本准则当形式，交付时补一张清单 | 提交历史仍然是乱的 |
