# 附录：个人偏好（用户层）

> 解决的问题：铁律层太重（写进去就是事故），项目层太重（只对某个仓成立）。
> 那些「我在哪个项目都这么干、但项目有理由时可以让步」的习惯，原先没有地方放——
> 塞进铁律会把底线稀释，每次重写进项目规则会漂移。这一层专门装它们。

---

## 0. 什么该写进这里（三问判断法）

| 判断 | 落哪 |
| --- | --- |
| 违反了就是事故（数据来源编造、静默兜底、每轮必须注入） | **铁律层**：正文 §2/§3/§5/§6/§7，不得写在这里 |
| 只对某个仓库成立（目录、命名、构建命令、框架约定） | **项目层**：目标仓库自己的规则文件 |
| 跨项目都想要，但某个项目有理由时可以让步 | **用户层**：本文件 |

补充规则：

1. **本文件不豁免铁律**：与正文冲突时以铁律为准；想让某条偏好压过铁律，那叫「升级为铁律」，去改正文，不是写在这里。
2. **本文件只提供默认值**：项目规则明确写了不同做法时，按项目规则执行，并在交付里说明"按项目规则偏离了个人偏好"。
3. **不放项目事实**：具体端口、目录、命令属于项目层，写进来会立刻过期。
4. **不写"我觉得"**：每条必须能落到可执行的行为上，并给出证据（往期做法、本仓文档、你明确说过的话）。

## 0.1 优先级（插在原来的三层之间）

```
用户当轮指令 > 铁律层 > 项目层 > 个人偏好层 > 技术栈附录默认值
```

个人偏好排在项目层之后：仓库怎么写的，比我的习惯更重要；排在附录默认值之前：附录给的是通用做法，我的习惯更具体。

## 1. 条目格式

| 列 | 要求 |
| --- | --- |
| 编号 | `U1`、`U2`……，只增不改号 |
| 领域 | 语言 / 结构 / 文档 / 脚本 / 提交 / 交互 等 |
| 偏好 | 一句可执行的话，带「做什么」和「不做什么」 |
| 强度 | `默认`（照做，除非项目不同）/ `偏好`（可偏离，交付说明理由）/ `强偏好`（偏离必须先问） |
| 证据 | 这条偏好从哪来：往期做法、本仓文档、你的原话 |
| 状态 | `生效` / `待确认`（待你确认的候选项，AI 不得按待确认项行事） |

## 3. 怎么新增与修改

1. **只在你明确表达后追加**：AI 不得从一次提问里推断你的长期偏好，也不得把自己的写法当成你的偏好。
2. **一次一条**：新增条目单独一行，带证据；没证据的先标 `待确认`。
3. **能合并就合并**：新条目和已有条目讲的是同一件事，改原条目而不是加一条平行规则。
4. **上限 40 条**：超了就说明这层正在变成第二份铁律，该挑出真正要强制的升级到正文。
5. **半年清理一次**：长期没触发过的、已经被项目规则完全覆盖的，删掉；删掉的在 §5 记一行。

## 4. 上下文成本

这层不写进常驻记忆（那是铁律的地盘），只在写代码任务开始时随正文一起读。所以每条都要短：一行说清，不写背景故事；超过两行的条目拆成两条或删掉。
