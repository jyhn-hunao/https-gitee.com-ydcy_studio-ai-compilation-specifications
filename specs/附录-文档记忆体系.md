# 附录：文档记忆体系（docs/ 增长型记忆目录）

> 解决的问题：**AI 换了会话、换了代理就忘了上次的结论**，于是反复问同样的问题、重复踩同一个坑、重复写一次性脚本。
> 本附录只规定"记什么、放哪、怎么命名、怎么让索引不失真"，不承载任何具体业务事实。

与另外四份技术栈附录不同：本附录**与技术栈无关**，可按项目整体启用或整体不用；启用后目录可删减，但第 0 节的三条底线建议不豁免。

---

## 0. 三条底线（启用即强制）

1. **只写已确认事实**：来源必须是代码、接口实际返回、日志、DDL、用户明确确认之一。未验证的猜测、"大概是"、临时方案一律不写。
2. **先索引后正文**：新增、删除、移动、改名任何一个记忆文件，**同一轮**必须更新最近一级 `README.md`；索引失真等于记忆不可检索，比不写更坏。
3. **禁写清单**：密钥/账号/token、一次性日志与调试输出、临时进度、代码一眼可见的事实、尚未确认且可能被推翻的方案、大段原始数据倾倒。

## 1. 目录骨架（可直接照抄，按项目删减）

```text
docs/
├── MEMORY_INDEX.md              # 唯一检索入口：只列目录入口 + 少量稳定根文档
├── architecture/               # 架构、仓库边界、职责划分
├── interfaces/                 # 接口路径、字段约定、消息结构、跨服务契约
│   ├── modules/<模块-slug>/     #   单模块接口
│   ├── cross-service/          #   跨仓/跨端稳定契约
│   ├── message-flow/           #   消息、回调、异步链路
│   └── archive/                #   已废弃契约
├── runbooks/                   # 操作步骤、联调顺序、排查流程、环境配置、验收方法
│   ├── workflows/  troubleshooting/
│   ├── environment/  validation/
│   └── archive/
├── pitfalls/                   # 高误判点、限制规则、排查结论
│   ├── modules/<模块-slug>/  backend/  frontend/  algo/  environment/
│   └── archive/
├── decisions/                  # 已确认的技术决策、开发约束、长期规则
│   ├── modules/<模块-slug>/  cross-module/  project-rules/  architecture-refactor/
│   └── archive/
├── function_realize/           # 功能新增/修改后的方法流转
│   ├── modules/<模块-slug>/  cross-module/  documents/  rules/
│   └── archive/
├── sql-log/                    # 需要人工执行/审核/追溯/归档的 SQL
│   ├── YYYY/MM/                #   普通记录：YYYY/MM/YYYY-MM-DD-动作-对象.sql
│   ├── templates/  archive/
│   └── YYYY/MM/<业务批次>/<分级>/<NNN-对象>/执行清单.md
├── handoffs/                   # 仅在用户明确要求时读写的交接记录
└── test-tools/                 # 临时/维护测试方法登记表（唯一事实源）
```

| 目录 | 收什么 | 不收什么 | 粒度 |
| --- | --- | --- | --- |
| `architecture/` | 工作区/仓库边界、模块职责、调用链骨架、长期结构约定 | 具体接口字段（→`interfaces/`）、一次改进方案（→`decisions/`） | 每仓/每模块 1~3 篇，稳定后很少变 |
| `interfaces/` | 接口路径、入参出参、字段语义、消息结构、跨服务契约、回调格式 | 前端展示细节、业务规则取舍（→`decisions/`） | 一个接口或一条消息 1 篇 |
| `runbooks/` | 可照做的操作步骤、联调顺序、排查流程、环境配置、验收方法 | 未复现的排障过程（→`pitfalls/`，且必须有结论） | 一次流程 1 篇 |
| `pitfalls/` | 已确认的高误判点、限制规则、排查结论（现象→原因→判据→绕法） | 未确认猜测、一次性报错堆栈 | 一个坑 1 篇 |
| `decisions/` | 已确认的技术决策、开发约束、长期规则，含"为何没选另一方案" | 待定方案、讨论过程 | 一个决策 1 篇，允许被新决策取代 |
| `function_realize/` | 功能新增/修改/修复后的方法流转：入口→主链→落库/返回 | 大段代码粘贴、逐行解释 | 一次功能变更 1 篇 |
| `sql-log/` | 需人工执行、审核、追溯、归档的 SQL | 代码内自动迁移脚本（随代码仓）、临时只读查询 | 一次维护 1 个文件 |
| `handoffs/` | 跨会话继续工作所需的上下文 | 历史流水账、完整过程记录 | 一次交接 1 篇 |
| `test-tools/` | 临时/维护测试方法的索引与基线 | 测试代码本身（在代码仓） | 登记表 1 份 |

非记忆目录（可选）：`task-artifacts/`（一次性清单、核对报告、导出文件，**不算长期记忆**）、`templates/`（文件模板）、`archive/`（过期但需留痕）。

## 2. 一眼判定：这条知识该放哪

```text
这条知识属于哪一类？
├── 一次性产物（清单、报告、导出、截图） ────────────→ task-artifacts/，不进长期记忆
├── 只对"下次接着干"有意义 ───────────────────────→ handoffs/（且只在用户明确要求时写）
├── 有 SQL 要人工执行/追溯 ───────────────────────→ sql-log/
├── 为维护写过测试方法、怕以后忘了用法 ─────────────→ test-tools/index.md
├── 变了会让别的调用方出错 ────────────────────────→ interfaces/（契约）/ architecture/（边界）
├── 已定的取舍，以后不许再争 ─────────────────────→ decisions/
├── 复现过、有结论的坑 ──────────────────────────→ pitfalls/
├── 可照做的操作/排查/验收步骤 ───────────────────→ runbooks/
├── 一次功能变更的方法流转 ───────────────────────→ function_realize/
└── 都不符合 ────────────────────────────────────→ 直接不写（代码本身能回答的，不写）
```

判定口诀：**契约看 interfaces，取舍看 decisions，坑看 pitfalls，步骤看 runbooks，流转看 function_realize，一次性看 task-artifacts。**

## 3. 命名、标题与文件头

| 类型 | 命名 | 示例 |
| --- | --- | --- |
| 坑点/决策/接口/Runbook | `YYYY-MM-DD-动作-对象.md` 或 `主题-YYYY-MM-DD.md` | `2026-03-11-修复-时段字段跨天边界.md` |
| 功能实现记录 | `YYYY-MM-DD-动作-功能名.md` | `2026-03-02-新增-批量导入.md` |
| 交接记录 | `YYYY-MM-DD-主题-handoff.md` | `2026-03-05-拓扑改造-handoff.md` |
| SQL | `YYYY-MM-DD-动作-对象.sql` | `2026-03-11-补充-历史数据回填.sql` |
| 索引 | 每级目录固定 `README.md` | — |

- 动作词表固定：`新增 / 修改 / 修复 / 重构 / 维护 / 补充 / 设计 / 迁移`。同一天同一对象多次维护时加稳定后缀 `-01`、`-02`。
- **标题写结论，不写主题泛词**：`XX 不能用 YY 判断` 优于 `关于 XX 的说明`。
- **一个文件只放一类事实、一个结论**；混合内容按类型拆到不同目录。
- 文件头建议 5 行内摘要：结论 / 影响范围 / 日期 / 关联文件或接口；用了笔记工具时可加 frontmatter，但 `README.md` 索引不要依赖工具才能读。

---

## 4. 索引维护规则（最容易失真的部分）

1. `MEMORY_INDEX.md` 只维护**目录入口 + 少量稳定根文档**，**不平铺列出增长型目录下的每个文件**。
2. 每个增长型目录、每个分类子目录都要有 `README.md`：写清"收什么、不收什么、新增落哪个子目录、如何拆分"。
3. 新增分类目录时，同时创建该目录 `README.md` 并更新上一级 `README.md`；目录变空就删目录并更新索引，不留死链。
4. 根目录不放业务记录文件；根文档只保留总览、已知缺口、环境基线、变更模板等稳定入口。
5. 若项目有自动校验能力，可对索引做链接可达性检查；没有就靠"同一轮更新"这条纪律。

---

## 5. 增长、拆分与归档

- 单一模块记录超过 **3 篇** → 建 `modules/<模块-slug>/README.md` 并迁入，更新上一级索引。
- 单个目录文件数超过 **20 个** → 按年月（`YYYY/MM/`）或按主题建子目录。
- 跨模块 / 跨仓 / 跨前后端记录 → 放对应 `cross-module/`，不塞进 `modules/misc/`。
- 过期记录**移入 `archive/` 并保留原来源线索**，不直接删除；`archive/README.md` 说明归档原因与日期。
- 拆分、归档、改名都算"移动"，必须同轮更新索引。

---

## 6. 三个特殊目录的硬约束

### 6.1 `handoffs/`：只能由用户触发

- **只在用户明确说"生成交接 / handoff / 下次继续用的记录"时创建或更新**；代理不得自行生成。
- 写了就代表**下一次会话要按它继续**：读到 handoff 时按其目标与未完成项推进，不脱离 handoff 自行另起主张。
- 必含要素：目标与当前状态、已确认事实/数据来源、已改文件、未完成事项、风险与待确认项、验证方式。
- 任务跨多仓、未完成验证、或结论依赖尚未取得的数据时，应**主动建议**写 handoff，但未经同意不写。

### 6.2 `sql-log/`：AI 生成、人工执行

- 默认只生成不执行；库写入、覆盖、删除必须由人确认执行。
- 状态机唯一路径：`待执行/` →（用户确认执行）→ `已执行待复核/` →（字段复核与缓存处理完成）→ `已完成/`。
- **已执行文件冻结**：不得改写其中 DML；执行后发现问题，新建 `补充维护-*.sql` 重新进 `待执行/`。
- 每批次的唯一执行入口是 `执行清单.md`；`查询/` 只放只读查询，不得当维护脚本执行。
- 每个 SQL 文件头至少说明：目的、适用环境/库、影响表、是否已执行、确认来源、回滚或核验方式。
- 禁止把多张单据合并成一份大 SQL；超过 20 个文件按年月归档。

### 6.3 `test-tools/`：唯一事实源 + 同轮登记

- 登记表是测试方法的**唯一事实源**，禁止在 `docs/` 其他位置再维护一份清单。
- 新增、修改、删除测试方法时，**同一轮**更新登记表，并在交付说明中写明"登记表已更新：新增/修改/删除 N 条"。
- 登记表顶部维护基线（文件数、用例命中数）；怀疑漂移时重新计数，不一致先补登记再做别的。
- 危险等级是**静态推断**（依据类注释、是否调用写方法、是否连真实依赖）；执行前仍要读方法体，标注"待确认"的必须人工确认。
- 故意不按测试框架命名规则命名的类（避免被自动收集执行）是保护措施，不要改名。

## 7. 检索与读取纪律

1. 顺序固定：`MEMORY_INDEX.md` → 对应目录 `README.md` → 关键词检索 `docs/**/*.md` → 直接读代码；启用第 11 节的记忆插件时，最前面加一次语义召回。
2. 一次检索没有命中就直接读代码，**不等待、不试探、不猜**；没有相关记忆不构成阻塞理由。
3. 读到与当前代码冲突的记录：**以代码为准**，并在同一轮修正该记录或标注"已过期，移至 archive"。
4. 记忆是历史参考，**不是当前指令**；与用户本轮明确要求冲突时，先说明冲突点再动手。

---

## 8. 冲突裁决

1. 用户当前指令 > 代码/接口事实 > 记忆记录。
2. 项目层约定（目录、命名、构建、框架写法）> 本附录默认值；但第 0 节三条底线不豁免。
3. 无法判断谁优先时停下问人，不自行扩大解释、不静默选一边。

---

## 9. 新项目接入清单

1. 建 `docs/` 与所需增长目录，每个目录一个 `README.md`（写明收什么/不收什么/新记录落哪）。
2. 建 `MEMORY_INDEX.md`：只列目录入口和稳定根文档。
3. 在项目规则文件里加**一行入口**指向本附录，并只写项目差异（额外目录、专用工具、口径）。
4. 在项目规则中声明检索顺序与写入时机（本节与第 7 节可直接抄）。
5. 入驻第一周至少写 1~2 篇真实记录，避免留下空骨架；空目录比没有目录更容易误导。

---

## 10. 反模式

| 反模式 | 后果 |
| --- | --- |
| 所有笔记平铺在 `docs/` 根目录 | 无法检索，索引必然失真 |
| `MEMORY_INDEX.md` 手写全量文件清单 | 每写一篇都要改索引，迟早漏改 |
| 记录只写"已修复" | 没有现象/原因/判据，下次照样踩 |
| 一个文件混多主题 | 归类矛盾，拆分时反复搬 |
| 过期记录直接删 | 丢掉"为什么当时这么定"的证据 |
| 把猜测写成事实 | 后续按错误结论改代码，危害大于不写 |
| 代理自行生成 handoff | 交接内容失真，下一会话被误导 |
| 索引不同步 | 死链与漏检，检索成本高于重读代码 |

## 11. 与其他记忆层的关系（启用记忆插件时）

若项目同时使用常驻记忆、语义召回库、任务看板记忆，按"**同一事实只写一处**"分层：

| 判断 | 落点 |
| --- | --- |
| 换工作区仍成立（个人偏好、铁律） | 常驻/全局记忆 |
| 换目标或换模块仍成立（本工作区通用知识） | 项目语义内存 + `docs/` 事实源（摘要进内存，正文进 docs） |
| 只对当前目标/任务有意义 | 任务看板或目标级记忆 |
| 完整叙事、可复查的结论 | `docs/` 对应目录（**事实源**） |

- 语义召回只是入口，**`docs/` 与代码才是事实源**；两者冲突以 `docs/` 与代码为准，并同轮修记忆。
- 检索顺序：语义召回 → `docs/` → 代码；召回为空不代表没有记忆。
- 写入依赖外部 CLI/服务时，失败要显式报告，不得当成"已记录"。
