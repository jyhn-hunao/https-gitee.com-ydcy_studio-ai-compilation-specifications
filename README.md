# AI-CompilationSpecifications

用于记录 AI 编写代码的规范文件。**本仓是规范本体（单一事实源）**——换机器、换项目都从这里取，不在别处再存一份。

## 目录结构

| 路径 | 内容 |
| --- | --- |
| `specs/个人编码与AI协作规范.md` | 主正文（技术栈无关）：任务分级与 dsh-graph 路由、**中文伪代码（写进代码的编号注释）**、编码铁律、交付八项、验收清单、提示词模板、反模式 |
| `specs/附录-后端-Java-SpringBoot.md` | 后端（Java/Spring Boot）技术栈附录 |
| `specs/附录-前端-Vue3.md` | 前端（Vue 3）技术栈附录 |
| `specs/附录-算法-Python-FastAPI.md` | 算法服务（Python/FastAPI）技术栈附录 |
| `specs/附录-数据-SQL与数据库.md` | 数据、SQL 与数据库附录 |

| `specs/附录-提交准则.md` | **通用协作附录（与技术栈无关）**：提交单元、粒度上下限（文件/行数/审查时长）、拆分策略、提交信息、审查视角与 AI 提交纪律 |

## 分层与优先级

1. **铁律层**（主正文第 2、3、5、6、7 章：任务分级与 dsh-graph 路由、中文伪代码（代码内编号注释）、先思路后代码、数据来源可证明、编码铁律、交付八项）——**任何项目不得豁免**；
2. **项目层**（目录、命名、构建命令、框架约定、既有风格）——服从所在仓库；
3. 无法判断谁优先时，停下来问人。

## 安装（在新机器上生效）

1. 落地规范本体：
   ```bash
   git clone https://gitee.com/ydcy_studio/ai-compilation-specifications.git ~/.dsh/standards
   ```
2. 把 `install/agents-pointer.md` 的内容**按标记块**并入 `~/.dsh/AGENTS.md`（插入或替换标记块之间的内容，**不要覆盖该文件里原有的其他规则**）。
3. 把 `install/iron-rules.txt` 交给该机器上的 AI 会话，要求它**写进常驻/全局记忆**。

三步缺任一步都会漏生效：第 1 步给正文，第 2 步给入口，第 3 步给每轮都注入的底线。

## 迁移到具体项目：AI 执行顺序（必读）

> 本节解决的问题：拉取本仓后，AI 如何把通用规则**完整**落到一个具体仓库——不漏项、不臆造、不把"待确认"擅自决定。
> 通用规范只给默认值；项目规范必须由目标仓库的证据生成。

### 三条硬性前提

1. **先读后写**：先完整读主正文 + 目标技术栈附录（无对应附录就只读主正文），未读完不得创建或修改项目规则。
2. **证据优先**：项目规范里的每个值（路径、命令、版本、目录、命名、端口、配置项）必须能指到目标仓库的具体文件；指不到就进"待确认"，**不许猜，也不许拿通用默认值冒充项目值**。
3. **只加规则不改业务**：迁移只创建/合并规则文件，不改业务代码；动手前先 `git status`，避开或兼容用户已有改动；已有规则文件按"合并、保留原内容"处理，禁止整篇覆盖。

### 执行顺序（0–8 步）

| 步 | 动作 | 产出 | 完成判据 |
| --- | --- | --- | --- |
| 0 | 登记版本与技术栈 | 通用规范版本/commit、技术栈清单 | 能说出用哪几份附录 |
| 1 | 仓库侦察（只读） | 事实清单：目录树、构建文件、测试、CI、配置样例、已有规则 | 每条事实带"文件路径:行" |
| 2 | 建/合并项目规则主文件 | `AGENTS.md`（或宿主等价文件） | 按下文骨架齐全，无占位符 |
| 3 | 技术栈落地 | 附录默认值 → 项目值的映射 | 不适用项写明理由 |
| 4 | 项目专属编码风格 | 分层/命名/注释/异常/日志/模型/持久层/前端/配置/测试 | 每条有正例（引用现有代码） |
| 5 | 提交准则落地 | scope 词表、阈值、验证命令、远程策略 | 引用《附录-提交准则》并写差异 |
| 6 | 验证与门禁 | 每条命令的实际执行结果（或未执行原因） | 不能把"没跑"写成"通过" |
| 7 | 待确认清单 | 问题、影响、可选方案、等谁确认 | 未确认项不得写成既成事实 |
| 8 | 自检与交付 | 迁移报告 | 下文的交付清单全过 |

**执行方式**：第 0–1 步只读；第 2 步起，每一步先把产出给人看，确认后再进下一步；第 7 步的待确认项未处理前，不得进入第 8 步交付。

### 按顺序创建的项目规范文件

按顺序建，不要跳步；路径按目标仓约定调整（下表是常见落位）。

| 顺序 | 文件 | 必建 | 作用 | 必须回答的问题 |
| --- | --- | --- | --- | --- |
| 1 | `AGENTS.md`（或 `CLAUDE.md` 等宿主规则文件） | 是 | 项目层唯一入口 | 项目定位；目录与代码归属；构建/启动/验证命令；后端/前端/数据约定；禁止项；交付要求；已知风险；与通用规范的裁决顺序 |
| 2 | 提交准则落地文件（如 `doc/commit-guidelines.md`，或 AGENTS.md 内章节） | 是 | 提交粒度与消息 | `type`/`scope` 词表；阈值覆盖（只能更严，放宽须给理由）；验证命令；本地/远程策略；1–2 个真实拆分示例 |
| 3 | `docs/MEMORY_INDEX.md` + 各目录 `README.md`（启用《文档记忆体系》时） | 启用即必建 | 长期事实检索 | 每个目录收什么/不收什么/新增落哪；索引更新时机 |
| 4 | `docs/architecture/`、`docs/interfaces/` 等（按需） | 推荐 | 结构与契约事实 | 模块边界、调用链、接口字段来源、跨端契约 |
| 5 | `.env.example`（涉及配置时） | 是（核对） | 环境变量清单 | 变量名、用途、默认值（假值）、是否敏感；真实值不入库 |
| 6 | 规则测试（项目有测试框架时） | 推荐 | 防规则回退 | 断言项目规则文件包含关键条目；不绕过、不失效 |
| 7 | 迁移报告（一次性） | 是 | 可核对 | 已落地/不适用/待确认三态；文件清单与验证结果 |

> `AGENTS.md` 默认入库、供团队共享。若团队要求把它作为个人本地文件（如 `skip-worktree`），必须在迁移报告里写明，并同时提供可复现的模板/说明，否则别人拉取后等于没有规则。

### 个性化编码风格：逐项定什么

"个性化"不是让 AI 自由发挥，而是**从目标仓库现有写法中提炼并固化**；找不到证据的项进待确认。

| 领域 | 必须写清 | 证据来源 | 禁止 |
| --- | --- | --- | --- |
| 分层与包结构 | Controller/Service/Mapper/Model/Core 边界；新文件落哪；调用链 | 现有目录与类 | 自创平行包、平行方法 |
| 命名与模型 | 类名后缀、`Qry*`/`*Param`/VO/DTO/Entity 规则 | 现有类名与字段 | 用 `data`/`temp` 承载业务概念 |
| 注释与文档 | 类头/方法 JavaDoc、编号伪代码、何时不补注释 | 现有代码 | 逐行注释、过期注释 |
| 异常与返回 | 统一返回结构、业务异常归属、错误文案 | 现有 Controller/Handler | 静默兜底、吞异常 |
| 依赖与日志 | 注入方式、日志注解、敏感字段禁打 | 现有类 | 混用注入方式、打印密钥 |
| 持久层 | ORM/XML 分工、分页、多方言、N+1 | 现有 Mapper/脚本 | 全表加载、内存分页 |
| 前端 | 目录、组件复用、API 目录、空态/加载态/失败态、样式与图标 | 现有 views/api/components | 页面直连 axios、复制组件另起一套 |
| 配置与环境 | 配置来源、环境变量读取入口、密钥处置 | `.env.example`、配置类 | 硬编码地址/账号/密钥 |
| 测试与验证 | 框架、必跑命令、无框架时的静态复核 | `package.json`、`pom.xml`、测试目录 | 未跑却写"已验证" |
| 提交 | `type`/`scope` 词表、阈值、远程策略、提交清单 | 《附录-提交准则》+ 团队约定 | 每次编辑即提交、超大提交 |

每条都写成「项目值 + 证据 + 例外」；例外必须说明触发条件，不能留"视情况而定"。技术栈附录里标注「示例」的条目来自具体项目，**先确认目标仓是否同样要求，未确认不得写入项目规范**。

### 两个模板（交付时必须有）

**迁移矩阵**（逐条对照通用规范）：

| 通用条款（章节） | 项目落地值 | 证据（文件:行） | 状态 |
| --- | --- | --- | --- |
| 例：§5.1 单方法 < 80 行 | 沿用 | `src/.../XxxService.java:42` | 已落地 |
| 例：§5.3 单一主入口 | 新逻辑改原方法，旧实现保留至 2026-12 | `XxxServiceImpl.java:88` | 待确认 |

状态只有三种：`已落地` / `不适用（理由）` / `待确认（问题编号）`。

**待确认清单**：

| 编号 | 待确认问题 | 为什么必须问 | 可选方案 | 影响 |
| --- | --- | --- | --- | --- |
| Q1 | 是否允许 AI 直接 push？ | 通用规范默认只落本地 | 允许/禁止/仅指定分支 | 提交与发布流程 |

规则：状态为"待确认"的项**不得**写进项目规则当既成事实；交付时列出并等确认。

### 自检与交付（缺一不算完成）

- [ ] "必建"文件全部存在且非空；
- [ ] 每个项目值有证据，或已列入待确认；
- [ ] 无 `TODO`/`TBD`/示例值/密钥/真实账号；
- [ ] 验证命令实际执行，或写明"未执行 + 原因"；
- [ ] 已有规则文件是合并，不是覆盖；
- [ ] 提交准则的 scope、阈值、远程策略已写；
- [ ] 迁移矩阵与待确认清单齐全，三态无遗漏；
- [ ] 有规则测试的项目，规则测试通过。

交付给用户的必须包含：**创建/修改的文件清单、迁移矩阵、待确认清单、验证命令与结果、与通用规范的差异说明**（只允许更严；放宽必须给理由并经确认）。

### 常见遗漏（对照检查）

| 遗漏 | 后果 | 纠正 |
| --- | --- | --- |
| 只写构建命令，不写测试/验证命令 | 没人知道怎么验 | 每条命令可复制执行 |
| 只写目录职责，不写"新代码落哪" | 新代码继续乱放 | 每个目录给落位规则 |
| 把通用规范整段复制进项目文件 | 两份漂移，改一处漏一处 | 项目文件只写差异与项目值 |
| 把"待确认"拍成默认值 | 错误规则被固化 | 列入清单问人 |
| 忽略仓库已有规则文件 | 覆盖用户约定 | 先合并，保留原内容 |
| 不写提交 scope/阈值 | 提交继续失控 | 按上文第 2 项建 |

### 维护

- 通用规范升级后：`git pull` → 看版本与 diff → 按迁移矩阵逐条复核 → 只改受影响条目 → 重跑规则测试。
- 项目规范只写"差异"，不复制通用正文；两边冲突按"用户当轮 > 项目规则 > 通用默认值"裁决。

## 已知边界

- 入口指针按 **DSH 宿主**写（读 `~/.dsh/AGENTS.md`）。换其他宿主（读 `CLAUDE.md`、`.cursorrules` 等）需按对方的约定改造入口指针。
- **常驻记忆必须经记忆工具写入**：`USER.md` / `MEMORY.md` / `memories.json` 里，Markdown 是生成投影，直接拷文件会在下一次写入时被覆盖。
- `~/.dsh/AGENTS.md` 会被宿主的会话规则字节预算挤掉（实测：项目规则文件 82KB 时，用户级规则整个没进上下文），所以铁律层必须落在常驻记忆里。
- 附录中标「示例」的条目来自具体项目（如禁用某个 CSS 属性），进入新仓库前先确认该仓是否同样要求，不要默认套用。
